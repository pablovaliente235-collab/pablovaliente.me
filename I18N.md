# Languages (EN default, ES) — how it works

One mechanism for the whole site: `/js/lang.js` (global `window.pvLang`).
English is the default and is what the HTML contains. Spanish is layered on top, so crawlers and no-JS visitors get English.

- Storage: `localStorage['pv-lang']` = `'en'` | `'es'`. No browser-language sniffing. The old `pv_lang` key is deleted on load.
- Every page has this snippet at the top of `<head>` (before the CSS), so `<html lang>` is right before the first paint:
  `<script>(function(){var l;try{l=localStorage.getItem('pv-lang')}catch(e){}document.documentElement.lang=(l==='es')?'es':'en';})();</script>`
- Every page loads `<script src="/js/lang.js"></script>` (before `kmenu.js`, and before any inline script that uses `pvLang`).
- The switch is in the kinetic menu foot (every page):
  `<div class="kmenu-lang" role="group" aria-label="Language"><button type="button" data-set-lang="en">EN</button><span>/</span><button type="button" data-set-lang="es">ES</button></div>`
  lang.js binds **every** `[data-set-lang]` button (also `.pf-lang` on start-a-project) and marks the active one with `.is-on` and `aria-pressed`.
  The legacy single toggles `#langToggle`, `#langToggleMobile`, `#langToggleOverlay` switch EN<->ES too and show the *other* language.

## API

```js
pvLang.get()            // 'en' | 'es'
pvLang.set('es')        // stores, sets <html lang>, translates the DOM, updates switches,
                        // fires listeners + document event 'pv:lang', and calls set() on same-origin iframes
pvLang.t('Hello','Hola')// picks the string for the current language (for text built in JS)
pvLang.on(fn)           // fn(lang) on every change; pvLang.on(fn, true) also calls it now
pvLang.apply(root)      // re-scan a subtree (call after you insert markup that carries data-es*)
document.addEventListener('pv:lang', e => e.detail.lang)
```
JS that builds text should render with `pvLang.t()` at start and re-render in `pvLang.on(...)`. Changes in other tabs are followed via the `storage` event.

## Translating page content: attributes

The English text stays in the HTML; add the Spanish as an attribute. lang.js remembers the English the first time it swaps and restores it on EN.

| Attribute | Effect |
|---|---|
| `data-es="Texto"` | replaces `textContent` (use only on elements without child markup you want to keep) |
| `data-es-html="Texto con <em>marcado</em>"` | replaces `innerHTML` (use for `<br>`, `<em>`, links…) |
| `data-es-aria` / `data-es-alt` / `data-es-title` / `data-es-placeholder` | set `aria-label` / `alt` / `title` / `placeholder` |
| `data-es-content` | `content` of a `<meta>` (description…) |
| `<title data-es="…">` | also updates `document.title` |

Example: `<p data-es-html="Línea uno<br>línea dos">Line one<br>line two</p>`,
`<meta name="description" content="…" data-es-content="…">`, `<img alt="…" data-es-alt="…">`.

Notes
- Elements inside `.kmenu-word` / `.kword` are handled by `kmenu.js`, not by `data-es` (see below).
- Don't put `data-es` on an element that contains the `.footer-year` span or other JS-managed nodes; put it on a wrapper of the static text instead.
- Keep proper names (film titles, hotel names…) untranslated.
- `<noscript>` content can't be translated (lang.js needs JS).

### Paired spans (used by dctl.html)
`<span class="en">Download</span><span class="es">Descargar</span>` — pure CSS (`html[lang="en"] .es, html[lang="es"] .en {display:none!important}`, in `kmenu.css`). Fine for short strings; prefer `data-es` for new content.

### `[data-i18n]` keys (`/js/i18n.js`)
Used by the photography pages (architecture/*, hospitality). `i18n = { en:{…}, es:{…} }`; `data-i18n="key"` swaps `textContent`, `data-i18n-aria="key"` swaps `aria-label`. `works.html` has its own small dictionary with the same mechanism. For new work prefer `data-es`.

## COMMON dictionary (automatic, no markup needed)

In `lang.js`: `COMMON` (text) and `COMMON_ATTR` (`aria-label` / `title`).
- `COMMON` is applied to text nodes (exact match of the trimmed text; surrounding whitespace is kept) inside `#site-header, #unified-header, #kmenu, #site-footer, footer, .pv-foot, .last-section, .end-label`.
  Includes: `Pablo Valiente. All rights reserved.`, `Start a project`, `Book a call`, `Mail`→`Email`, `Impressum`→`Aviso legal`, `MENU`/`CLOSE`, `Next Work`, `Get in touch`, …
- `COMMON_ATTR` is applied to every `aria-label`/`title` in the page with an exact match (`Open menu`, `Close menu`, `Site footer`, `Main menu`, `Client reviews`, `Previous slide`, `Play/Pause`, …).
- To add a shared string: add it to the object in `lang.js`. An element with its own `data-es` always wins over COMMON.
- The kinetic menu marquee (client reviews) stays English on purpose; only its aria-label is translated.

## Kinetic menu words
`kmenu.js` splits each `.kmenu-word` / `.kword` into `.ch` letters. English text is kept in `data-en`; Spanish comes from `data-es` on the element or from the map in `kmenu.js` (`Photography`→`Fotografía`, `About`→`Sobre mí`, `Contact`→`Contacto`; `Film` and `DCTLs` stay). On every language change the words are re-split. For a `.kword` (kinetic list on contact.html) put `data-es="…"` on the `.kword` element itself.
`MENU`/`CLOSE`, the burger `aria-label` and the injected "Book a call" link are translated by `kmenu.js` via `pvLang`.

## Adding a page
1. `<html lang="en">`, the head snippet above, `<script src="/js/lang.js"></script>` before `kmenu.js`.
2. The kmenu markup with the `.kmenu-lang` switch in `.kmenu-foot` (copy from any page).
3. Footer text needs nothing (COMMON). Body text: `data-es` / `data-es-html`. `<title data-es>` and `data-es-content` on the description.
4. Text generated by JS: `pvLang.t()` + `pvLang.on()`; after inserting markup with `data-es*` call `pvLang.apply(container)`.

## Embedded pages
`index.html` embeds `works.html` in an iframe. `pvLang.set()` calls the same function in same-origin iframes; the iframe's own lang.js reads the stored value on load.

## Real Spanish URLs (URL pairs) — service pages

Besides the client-side switch, the service pages exist as real, indexable Spanish URLs under `/es/`:

| EN | ES |
|---|---|
| `/services/` | `/es/servicios/` |
| `/services/remote-video-editing-color-grading/` | `/es/servicios/edicion-video-etalonaje-remoto/` |
| `/services/real-estate-video-photography/` | `/es/servicios/video-fotografia-inmobiliaria/` |
| `/services/hotel-hospitality-video-production/` | `/es/servicios/video-hoteles-hosteleria/` |
| `/services/brand-commercial-video-production/` | `/es/servicios/video-publicitario-marca/` |

- **ES pages are static Spanish** (`<html lang="es">`, all text in the HTML, no `data-es` for page content; reviews stay English quotes with `lang="en"`). Same layout/CSS (`/css/services.css`). They were generated from the live EN pages (their `data-es` texts), so the Spanish copy lives in two places: if you edit a service page, edit its counterpart too. SEO title/description are written for Spanish searches (not the same as the `data-es` title of the EN page).
- **Counterpart meta** on both pages of a pair: `<meta name="pv-alt-en" content="/services/…/">` and `<meta name="pv-alt-es" content="/es/servicios/…/">`. When the visitor clicks EN/ES (or a legacy toggle) and the page has the counterpart meta for the target language, lang.js stores `pv-lang` and **navigates** to that URL instead of swapping text. Pages without the meta behave as before.
- **`/es/` forces Spanish**: lang.js sets `pv-lang='es'` and `<html lang="es">` on any path starting with `/es/` (so menu/footer/COMMON stay Spanish and the preference follows the visitor). The head snippet on ES pages is `(function(){document.documentElement.lang='es';})();`. `storage` events are ignored there.
- **EN page + stored 'es' -> redirect.** The head snippet of the EN service pages is
  `<script>(function(){var l;try{l=localStorage.getItem('pv-lang')}catch(e){}if(l==='es'){location.replace('/es/servicios/…/'+location.search+location.hash);return}document.documentElement.lang=(l==='es')?'es':'en';})();</script>`
  It runs before anything is painted. Only an explicit stored `'es'` redirects; crawlers (no storage) and new visitors stay on English.
- **`hreflang` + canonical** on all 10 pages: `en`, `es`, `x-default` (= EN URL); canonical = self. Same alternates (`xhtml:link`) in `sitemap.xml`.
- **`data-es-href="/es/…"`** (generic, lang.js): when lang is `es` the element's `href` is replaced by this value; EN restores the original. Used for: the kinetic-menu "Services" link on every page (`/services/` -> `/es/servicios/`; `kmenu.js` still scrolls to the zone on the desktop home because it only checks `data-go`), the home zone-3 card links + "All services", the mobile home Services tab (the `navigateTo(...)` calls pick the URL with `pvLang.get()`), and links between the EN service pages.
- **To add another pair:** create the `/es/…/` page, add both `pv-alt-*` metas + the three `hreflang` links to both pages, add the redirect snippet to the EN page, add `data-es-href` to EN links that should follow the language, add both URLs (with `xhtml:link` alternates) to `sitemap.xml`.

## Spanish style
Spain Spanish, informal-professional. Kept in English: `Film` (menu word), `DCTLs`, `Software`, product names, project/film/hotel names. `Photography`→`Fotografía`, `About`→`Sobre mí`, `Contact`→`Contacto`, `Impressum`→`Aviso legal`, `Start a project`→`Empezar un proyecto`, `Book a call`→`Reservar una llamada`, `Japanese Sanctuary`→`Santuario japonés`.

## Page transitions (`/js/transition.js`)
Every page loads it (`defer`, in `<head>`, right after the lang snippet together with the anti-flash `html.pv-entering` snippet). It intercepts internal same-origin link clicks and shows a kinetic-type cover with the destination name, then navigates. Labels: kmenu link → its `.kmenu-word` text (already EN/ES); else `data-transition-label` on the link; else the path map inside the script (uses `pvLang.t`); else the link text (≤24 chars) or "Pablo Valiente". Add new pages to `NAMES` in `transition.js`. Opt out per link with `data-no-transition`. JS navigation: `pvTransition(url, label?, {kicker?, lang?})`.
